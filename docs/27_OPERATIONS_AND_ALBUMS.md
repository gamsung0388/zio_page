# 홈페이지 운영과 앨범 연결

2026-10-23. 기존 Workers·D1 인증과 노래·일정 데이터를 유지하면서 운영 기능을 확장합니다.

## 지오가 사용하는 순서

1. **노래 관리 → 새 노래 등록/수정 → 앨범 찾기**: 곡명·가수로 검색합니다. 원곡, 라이브, 반주 버전을 확인하고 한 후보를 선택하세요. 미국 검색에서도 한국 곡을 찾을 수 있습니다. 저장해야 표지와 공식 음원 링크가 반영됩니다. 곡명·숙련도·풍·비공개 메모는 자동으로 바꾸지 않습니다. 새 곡에서는 선택한 음원의 곡명·가수를 가져오는 버튼을 별도로 제공합니다. 연결 해제 시 기본 커버로 돌아갑니다.
2. **모바일 노래책자**: 검색창을 먼저 보여주고 상세 필터는 펼쳐서 사용합니다. 적용 중인 필터 개수를 표시합니다. 검색·필터·정렬·페이지는 기존 URL 상태를 유지합니다.
3. **관리 → 홈페이지 관리**: 기본 정보에서 메인 제목·소개·지오 소개·공식 HTTPS 링크 5개·추천 곡 4개까지 수정합니다. 추천 곡은 선택한 순서로 표시합니다. 추천 곡이 없거나 모두 비공개/삭제 상태이면 최신 공개 곡을 보여줍니다. SOOP 주소는 메뉴 구성에 있는 방송국 주소를 공통으로 사용합니다. 기존 메뉴 추가·이름·순서·표시와 테마 설정도 같은 관리 축에 있습니다.
4. **노래 휴지통 / 일정 휴지통**: 삭제한 노래와 개별 일정을 복원합니다. 노래는 메모와 앨범 연결을 유지하고 비공개로 복원합니다. 일정은 기간과 시간을 유지합니다. 영구 삭제는 확인 후 실행하고 되돌릴 수 없습니다. 자동 삭제는 없으며 직접 영구 삭제할 때까지 보관합니다. 주간 이미지 메모는 기존 별도 삭제 방식이며 이 휴지통의 대상이 아닙니다.
5. **노래 복사 / 선택 곡 일괄 수정**: 복사는 원본을 유지한 새 비공개 곡을 준비하며 관리자 메모는 복사하지 않습니다. 목록에서 최대 20곡을 골라 숙련도·연습 상태·풍·공개 여부 중 한 항목을 바꿉니다. 다른 곳에서 먼저 변경되거나 삭제된 곡은 건너뛰고 성공/충돌 개수를 알려줍니다. 최신 목록에서 다시 선택하세요.
6. **관리자 관리**: 다른 관리자의 사용 중지·재개와 모든 기기의 로그인 해제가 가능합니다. 사용 중지는 현재 세션도 폐기하며 노래·일정을 삭제하지 않습니다. 재개는 기존 비밀번호를 유지합니다. 내 계정 중지 및 마지막 활성 관리자 중지는 서버에서도 차단합니다. 기존 비밀번호 변경·초기화 메뉴는 유지합니다. 관리자 간 권한 차이는 없습니다.

**최근 변경 기록**은 노래·개별 일정의 등록/수정/휴지통/복원/영구 삭제와 관리자 사용 상태·로그인 해제를 기록합니다. 변경 전후의 전체 데이터나 비밀번호·메모 본문은 기록하지 않습니다. 과거 수정 내용으로 되돌리는 버전 복원 기능은 아닙니다. 도입 전 작업 이력은 소급 생성하지 않습니다.

## 백업

- **전체 CSV 백업**은 기존 10개 컬럼을 유지합니다. 앨범 연결 정보는 포함하지 않습니다. CSV 가져오기는 기존처럼 일괄 추가 방식이며 기존 곡을 덮어쓰지 않습니다.
- **앨범 포함 JSON 백업**은 활성 노래의 공개/비공개 정보·관리자 메모·앨범 연결을 함께 저장합니다. 100곡 단위로 서버에서 읽고 최대 10,000곡/12MB를 지원합니다. 더 큰 백업은 운영 SQL 도구를 사용합니다.
- **JSON 백업 가져오기**는 파일 전체 형식을 검증한 뒤 한 곡을 선택해 새 등록 화면에 준비합니다. 관리자 메모도 유지하므로 관리자만 사용할 수 있고, 공개 여부는 비공개로 시작합니다. 저장 전에는 DB를 변경하지 않습니다. 기존 곡과 중복되지 않는지 확인하세요. 계정이 바뀌면 메모리의 미확정 백업 선택은 정리됩니다.
- SQL 복구 검증은 원본 database.sql을 보존하고, 여기에서 추출한 precreate-schema.sql(모든 테이블) → restore-data.sql(나머지 원본 구문) 순서로 격리 DB에 적용합니다. 세 파일을 함께 보관하며 실제 복원도 이 순서를 지켜야 합니다. 뒤에 생성되는 테이블 참조와 트리거 이력을 보존합니다.
- SQL 전체 백업은 `npm run backup:verify -- --remote`로 생성하고 격리된 로컬 DB에 복원해 무결성을 검사합니다. SQL 백업은 Git에 포함하지 않습니다.

## 무료 플랜을 고려한 구성

- Vue 정적 자산과 기존 Worker/D1을 사용합니다. 새 유료 리소스·예약 작업·방문자별 외부 앨범 검색은 추가하지 않습니다.
- 앨범 검색은 인증된 관리자의 버튼 요청에서만 호출합니다. 전체 서비스 기준 분당 외부 검색 10회, 검색 결과 10분 캐시, 최대 캐시 100건, 요청당 후보 10개와 8초 타임아웃을 적용합니다. 외부 장애가 있어도 앨범 없이 노래를 저장할 수 있습니다.
- 검색 결과는 자동 확정하지 않습니다. 음원 정보·표지는 제공처 데이터이며 검색 국가와 음원 판본에 따라 결과가 다를 수 있습니다. 원본 API가 제공하는 이미지 URL을 사용합니다.
- 공식 음원 출처 링크와 Apple에서 배포한 iTunes 배지를 표지 근처에 표시합니다. 음원/가사 다운로드나 오디오 재생은 추가하지 않습니다.
- 공개 API는 비공개 곡과 메모를 조회하지 않으며, 홈페이지 추천에서도 공개 여부를 매번 확인합니다. 모든 쓰기는 기존 Origin·CSRF·세션·초기 비밀번호 변경 검사를 거칩니다.
- 일반 삭제는 `deleted_at`과 증가하는 revision을 이용합니다. 복원 후에도 오래 열린 편집창이 덮어쓸 수 없습니다. 변경 이력은 같은 SQL 트랜잭션의 트리거에서 기록합니다. 일괄 수정은 전체 실패 대신 각 곡의 revision 결과를 구분합니다.

## 코드 관리

- `shared/album.js`: 제공처·이미지·출처 URL 허용 목록과 앨범 데이터 검증.
- `server/services/catalog.js`: 외부 검색·캐시·횟수 제한. 기존 노래 저장 서비스와 분리합니다.
- `AlbumPicker`, `AlbumSource`, `CoverImage`: 등록·수정·목록·상세가 공통 컴포넌트를 사용합니다.
- `shared/site-profile.js`와 `server/repositories/versioned-setting.js`: 홈페이지 설정 검증과 revision 기반 설정 저장. 기존 테마 저장도 공통 저장 함수를 사용합니다.
- `server/repositories/recovery.js`, `operation-validation.js`: 노래·개별 일정의 복구/영구 삭제/페이지 검증 공통 처리. 테이블은 서버 허용 목록으로 고정합니다.
- `server/services/song-bulk.js`, `admin-status.js`: 노래 일괄 수정과 계정 상태 처리처럼 각 업무에만 해당하는 함수를 분리합니다.
- `shared/song-backup.js`와 `src/services/song-backup.js`: 백업 파일 검증과 페이지 다운로드/미확정 복원 선택을 분리합니다.

기존 라우터를 유지하고 `/admin/site`, `/admin/recovery`를 추가합니다. `/admin/menus`, `/admin/appearance`도 계속 사용할 수 있습니다. 관리자 관리와 노래·일정 운영 메뉴는 분리합니다.

## DB 적용과 배포

실행 migration은 `migrations/0009_song_albums.sql`, `0010_operation_recovery.sql`입니다. 설계용 `database/migrations/0001_initial.sql`과 사용자 ZIP은 수정하거나 실행하지 않습니다.

1. 단위/API·브라우저·참고 UI·운영 빌드를 검증합니다.
2. 운영 SQL 백업과 별도 로컬 복구 검증을 완료합니다.
3. `npm run db:migrate:remote`로 새 migration만 적용합니다.
4. `npm run deploy`로 Worker와 정적 자산을 함께 배포합니다.
5. 운영 자산의 해시, 공개 API/관리자 비인증 차단, 두 도메인과 주요 화면을 확인합니다. 운영 콘텐츠를 테스트용으로 만들거나 삭제하지 않습니다.

코드 버전만 롤백해도 추가된 컬럼은 유지해야 합니다. 휴지통 도입 이전 버전은 삭제 행을 고려하지 않으므로 운영 중인 데이터가 있는 상태에서 이전 Worker로 무작정 롤백하지 마세요. SQL 전체 복원은 별도 운영 절차로 판단합니다.
